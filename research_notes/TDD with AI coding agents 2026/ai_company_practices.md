# How AI and developer-tool companies said coding agents should use tests in 2026 (test-first / TDD focus)

Scope note: research date 18 Nov 2026. I fetched these primary sources directly: the Claude Code docs (best-practices and common-workflows pages, both live and undated), the claude.dev post by Addy Osmani (16 Nov 2026), the claude.com post by Delba de Oliveira (22 Jul 2026), Cursor's agent best-practices post (Lee Robinson, 9 Jan 2026), OpenAI's Codex best-practices guide (live and undated), Simon Willison's Agentic Engineering Patterns chapters, Mitchell Hashimoto's adoption post (5 Feb 2026) and Birgitta Böckeler's martinfowler.com experiment. For Google (Gemini CLI/Jules/testing blog), Vercel, GitHub Copilot agent, Cognition/Devin, Armin Ronacher and Geoffrey Huntley, I found **no** 2026 primary source specifically about tests or TDD (see Gaps). Anything marked "secondary" comes from search-result summaries or third-party write-ups and was not confirmed against the original.

## 1. Do they recommend writing a failing test first (red/green) with agents, and why?

### Takeaway
Most 2026 guidance from the main vendors and practitioners endorses test-first or reproduce-first as one way to give an agent a pass/fail target. The point is a closed verification loop, and the red step proves the test actually exercises the change. Cursor (Jan 2026) and Simon Willison (Feb 2026) say this most plainly. Anthropic's current docs fold it into a wider "give Claude a check to run" principle. A notable 2026 dissent is Thoughtworks' Birgitta Böckeler: her experiment found no clear benefit, and she has stopped telling agents to write tests first.

### Cited Findings
**Anthropic: Claude Code docs (live, undated pages fetched Nov 2026)**
- The best-practices page gives this as its model "good prompt" for a bug: *"users report login fails after the session times out. look at token refresh in src/auth/, write a failing test that reproduces it, then fix it"* (contrasted with the weak prompt *"fix the login bug"*). — [Claude Code: Best practices](https://code.claude.com/docs/en/best-practices)
- Core principle: *"Claude stops when the work looks done. If it has nothing to run that tells it whether the work actually is done, 'looks done' is all it has to go on. In practice that makes you the test suite."* And: *"Give Claude something it can run that comes back pass or fail. Once it has that, it can keep going on its own and you don't have to watch."* — [Claude Code: Best practices](https://code.claude.com/docs/en/best-practices)
- Checklist for unattended runs: *"Does it know what done looks like? A goal condition, a spec file, or a failing test it has to turn green."* and *"Can it check its own work? The test suite, a `Stop` hook, some kind of review step."* — [Claude Code: Best practices](https://code.claude.com/docs/en/best-practices)
- It lists ways to make the check stricter: a prompt (*"run the auth tests after, and keep going until they pass"*), `/goal` (a separate model checks the condition after every turn), a `Stop` hook (exit code 2 blocks the turn from ending), and `/code-review` in a fresh subagent. — [Claude Code: Best practices](https://code.claude.com/docs/en/best-practices)
- The current Common workflows page has **no explicit TDD recipe**. Its bug-fix tip is *"Tell Claude the command to reproduce the issue and get a stack trace"*. The testing recipe is test-after: *"add tests for the notification service" … "run the new tests and fix any failures"*. — [Claude Code: Common workflows](https://code.claude.com/docs/en/common-workflows)

**Anthropic: Claude Code team posts**
- Addy Osmani's "How the Claude Code team thinks about verification" (claude.dev, **16 Nov 2026**) does **not** discuss TDD, test-first or failing-test-first workflows (confirmed on full fetch). It frames verification around end-to-end runs, a `verify` skill, property and differential tests, and checks the change cannot edit (see Q3/Q4). — [claude.dev, 16 Nov 2026](https://claude.dev/blog/how-the-claude-code-team-thinks-about-verification/)
- Delba de Oliveira (Claude Code team), "Building verification loops in Claude Code with skills" (**22 Jul 2026**): defines a verification loop as *"an iterative process where Claude checks and attempts to fix the work"*. Claude draws on *"deterministic signals in your codebase, including type checkers, linters, tests, and runtime errors"*, and the post advises listing *"your exact build and test commands"* in CLAUDE.md. No mention of TDD or test-first. — [claude.com blog, 22 Jul 2026](https://claude.com/blog/building-verification-loops-in-claude-code-with-skills)
- Boris Cherny (creator of Claude Code), X thread of **2 Jan 2026** (secondary; original not fetched): *"give Claude a way to verify its work. If Claude has that feedback loop, it will 2-3x the quality of the final result."* The methods he names are browser testing via the Chrome extension, bash commands and test suites. That is verification in general, not TDD as such. — [VentureBeat summary](https://venturebeat.com/technology/the-creator-of-claude-code-just-revealed-his-workflow-and-developers-are); [Karo Zieminski summary](https://karozieminski.substack.com/p/boris-cherny-claude-code-workflow)

**Cursor: "Best practices for coding with agents", Lee Robinson, 9 Jan 2026**
- This is the most explicit vendor TDD recipe of 2026. Steps quoted from the post: *"Be explicit that you're doing TDD so it avoids creating mock implementations for functionality that doesn't exist yet."* → *"Tell the agent to run the tests and confirm they fail."* → *"Explicitly say not to write implementation code at this stage."* → *"Commit the tests"* → *"Ask the agent to write code that passes the tests"*, instructing it *"not to modify the tests"* → *"Tell it to keep iterating until all tests pass."* → *"Commit the implementation"*. — [Cursor blog, 9 Jan 2026](https://cursor.com/blog/agent-best-practices)
- Rationale: *"Agents perform best when they have a clear target to iterate against."* *"Tests allow the agent to make changes, evaluate results, and incrementally improve until it succeeds."* *"AI-generated code can look right while being subtly wrong."* — [Cursor blog, 9 Jan 2026](https://cursor.com/blog/agent-best-practices)

**OpenAI: Codex best-practices guide (developers.openai.com/codex/learn/best-practices now redirects to learn.chatgpt.com; undated live page)**
- Test-driven but not strictly test-first: *"Ask it to create tests when needed, run the relevant checks, confirm the result, and review the work before you accept it."* Prompts should state done criteria *"such as tests passing, behavior changing, or a bug no longer reproducing"*. It also says *"Codex can do this loop for you, but only if it knows what 'good' looks like."* — [OpenAI Codex best practices](https://learn.chatgpt.com/guides/best-practices)
- A good AGENTS.md covers *"Build, test, and lint commands"* and *"What done means and how to verify work"*. Common mistake: *"Not letting the agent see its work by not giving details on how to best run build and test commands."* — [OpenAI Codex best practices](https://learn.chatgpt.com/guides/best-practices)
- The fetched page does not prescribe red/green or failing-test-first. — [OpenAI Codex best practices](https://learn.chatgpt.com/guides/best-practices)

**Simon Willison: Agentic Engineering Patterns (guide launched 23 Feb 2026; chapter pages are undated living documents)**
- *"'Use red/green TDD' is a pleasingly succinct way to get better results out of a coding agent."* It is *"a fantastic fit for coding agents."* Process: *"You write the automated tests first, confirm that they fail, then iterate on the implementation until the tests pass."* — [Willison, Red/green TDD](https://simonwillison.net/guides/agentic-engineering-patterns/red-green-tdd/); launch post: [simonwillison.net, 23 Feb 2026](https://simonwillison.net/2026/feb/23/agentic-engineering-patterns)
- Why confirm red: *"If you skip that step you risk building a test that passes already."* The risks he names: *"A significant risk with coding agents is that they might write code that doesn't work"*, and unnecessary code that *"never gets used"*. Test-first guards against both. — [Willison, Red/green TDD](https://simonwillison.net/guides/agentic-engineering-patterns/red-green-tdd/)
- The companion chapter "First run the tests" says *"Automated tests are no longer optional when working with coding agents"* and *"If the code has never been executed it's pure luck if it actually works when deployed to production."* Running the suite first *"tells the agent that there is a test suite and forces it to figure out how to run the tests"* and *"puts the agent in a testing mindset."* — [Willison, First run the tests](https://simonwillison.net/guides/agentic-engineering-patterns/first-run-the-tests/)

**Mitchell Hashimoto: "My AI Adoption Journey", 5 Feb 2026**
- *"If you give an agent a way to verify its work, it more often than not fixes its own mistakes and prevents regressions."* He names the practice "harness engineering": *"anytime you find an agent makes a mistake, you take the time to engineer a solution"*, ideally *"fast, high quality tools to automatically tell it when it is wrong"*, e.g. *"scripts to take screenshots, run filtered tests, etc etc."* He does not prescribe TDD specifically. — [mitchellh.com, 5 Feb 2026](https://mitchellh.com/writing/my-ai-adoption-journey)

**Dissent: Birgitta Böckeler (Thoughtworks), "TDD inside the agent loop - theater or actual value?" (martinfowler.com; page undated, secondary write-ups place it in Aug 2026)**
- An exploratory comparison of agent runs with and without TDD instructions on small, medium and large greenfield business-logic tasks. Sonnet 4.6 generated the code and Opus 4.8 judged it blind. Conclusion: *"there was no clearly discernable difference based on TDD workflow versus no TDD workflow"*. Also: *"The experiment at least hasn't demonstrated superior design in the TDD runs at all"* and *"The TDD instructions actively work against such an up front design step."* Her stance: *"I personally have stopped telling my coding agents to write tests first."* — [martinfowler.com (Böckeler)](https://martinfowler.com/articles/exploring-gen-ai/tdd-in-the-agent-loop.html); date per [daily.dev summary](https://daily.dev/posts/tdd-inside-the-agent-loop---theater-or-actual-value--mytwhkuys)
- Opposing view (secondary): The Register's report on an Agile Manifesto anniversary workshop (**20 Feb 2026**) quotes the claim that *"TDD prevents a failure mode where agents write tests that verify broken behavior. When the tests exist before the code, agents cannot cheat by writing a test that simply confirms whatever incorrect implementation they produced."* — [The Register, 20 Feb 2026](https://www.theregister.com/2026/02/20/from_agile_to_ai_anniversary/) (quote from a search summary, not verified on page)

**Reproduce-first for bugs (related research)**
- FixedBench (May 2026 paper, secondary summary) reports that agents *"jump directly to reading source code and crafting patches without first attempting to reproduce the reported bug"*. On instances where the bug was already fixed, running the reproduction would have shown the test already passes, so the right move is no change. — [Daniel Vaughan summary of FixedBench, 19 Jun 2026](https://codex.danielvaughan.com/2026/06/19/coding-agents-fixing-correct-code-fixedbench-codex-cli-abstain-reproduce-before-patch-action-bias/)

### Inferences
- The strongest common thread is not "TDD" but **give the agent a machine-checkable definition of done before it starts**. A failing test is the most common form, but goal conditions, specs, screenshots and E2E runs count equally in Anthropic's, OpenAI's and Hashimoto's framing.
- The rationales given for the red step: (a) prove the test actually exercises the change (Willison); (b) stop the agent writing mock implementations or code early (Cursor); (c) stop tests from confirming whatever the agent built (Agile workshop, secondary); (d) avoid "fixing" a bug that does not reproduce (FixedBench). Anthropic's own bug prompt ("write a failing test that reproduces it, then fix it") matches (a) and (d).
- Anthropic's 2026 materials have moved the emphasis away from unit-level TDD towards end-to-end verification (see Q3). That is consistent with, though not caused by, Böckeler's null result.

### Gaps
- No 2026 primary source from Google (Gemini CLI, Jules, Google Testing Blog), Vercel (v0 or engineering blog), GitHub Copilot coding agent, or Cognition/Devin on test-first workflows turned up in my searches.
- I did not fetch Boris Cherny's original X thread, so the "2-3x" quote is via secondary sources.
- The Willison chapter pages carry no date of their own. The red/green chapter appears to have been part of the 23 Feb 2026 launch, but this is inferred from search results.
- I found no 2026 test-specific post from Armin Ronacher or Geoffrey Huntley. Ronacher's 2026 posts (e.g. "A Language For Agents", 9 Feb 2026) were not fetched.

## 2. Should test-first tests be kept, or are they disposable scaffolding? Pruning and test bloat?

### Takeaway
No source I found treats test-first tests as throwaway scaffolding. Cursor says to commit them, and Willison says red/green yields a durable regression suite. The newest Anthropic post (Nov 2026) adds explicit pruning guidance. Test suites "only grow if you let them", so the team tidies them on a routine. Flaky tests whose cause cannot be found get deleted, with the reason written down. Anthropic's docs also warn that over-eager review produces "tests for cases that can't happen".

### Cited Findings
- Cursor: *"Commit the tests"* before implementation, then *"Commit the implementation"*. The tests are durable artefacts committed to version control. — [Cursor blog, 9 Jan 2026](https://cursor.com/blog/agent-best-practices)
- Willison: test-first *"ensures a robust automated test suite that protects against future regressions"* and *"A comprehensive test suite is by far the most effective way to keep those features working."* — [Willison, Red/green TDD](https://simonwillison.net/guides/agentic-engineering-patterns/red-green-tdd/)
- Willison on maintenance cost now that code is cheap: tests were *"time consuming and expensive to constantly rewrite while a codebase is rapidly evolving"*, but an agent *"can knock them into shape in just a few minutes."* — [Willison, First run the tests](https://simonwillison.net/guides/agentic-engineering-patterns/first-run-the-tests/)
- Willison (secondary summary of his "agentic manual testing" chapter): when manual testing by an agent finds a failure, have it fixed with red/green TDD so the case ends up in the permanent automated suite. — [Willison, Agentic manual testing](https://simonwillison.net/guides/agentic-engineering-patterns/agentic-manual-testing)
- Anthropic (Osmani, 16 Nov 2026): *"Rules need cleaning up too. Test suites, verification steps and .md files only grow if you let them, so we tidy them up on a routine."* — [claude.dev, 16 Nov 2026](https://claude.dev/blog/how-the-claude-code-team-thinks-about-verification/)
- Anthropic (Osmani, 16 Nov 2026), on flaky tests: *"Claude can't skip them, add sleeps or retry until they pass. If it can't find the root cause, it deletes the test and writes down why."* — [claude.dev, 16 Nov 2026](https://claude.dev/blog/how-the-claude-code-team-thinks-about-verification/)
- Anthropic docs, on over-testing from reviewers: *"A reviewer that's asked to find problems will always find something. If you fix every finding, you end up with extra abstraction layers and tests for cases that can't happen."* (Hence the advice to keep *"skip style"* in review prompts.) — [Claude Code: Best practices](https://code.claude.com/docs/en/best-practices)
- Böckeler's experiment found test counts varied widely, with TDD runs sometimes producing *fewer* tests (e.g. 21 and 20 vs 61 and 58 on the small task). — [martinfowler.com (Böckeler)](https://martinfowler.com/articles/exploring-gen-ai/tdd-in-the-agent-loop.html)

### Inferences
- The 2026 consensus is "keep and commit", balanced by active hygiene: prune flaky or low-value tests on a routine, and do not let reviewer agents pad the suite with tests for impossible cases. Explicit "delete your TDD scaffolding" advice did not appear in any source.

### Gaps
- No source gave a quantitative threshold or heuristic for when to delete a test, beyond Anthropic's flaky-test rule.

## 3. End-to-end tests, verify skills, property tests and differential tests versus unit tests

### Takeaway
Anthropic's Claude Code team (Nov 2026) has made the clearest statement. If you have to pick one test type for agents, pick end-to-end, because E2E tests are "difficult to fool". "Running the app end to end matters more than tests", and a fast, reliable `verify` skill is how Anthropic tests "nearly all changes". Property tests, with edge cases generated free of the agent's bias, and differential tests, for migrations, are recommended as complements. Unit tests are seen as fast but foolable.

### Cited Findings
- On unit tests: *"While unit tests are faster and less flaky, it's possible to pass them and still break the feature. This is because both the agent and the test don't understand the full task."* — [claude.dev (Osmani), 16 Nov 2026](https://claude.dev/blog/how-the-claude-code-team-thinks-about-verification/)
- On E2E: *"If you have to focus on one test type, pick end-to-end."* *"The reason E2E tests are so effective is that they are difficult to fool–either the whole feature works or it doesn't. They also have definitive done criteria and can concretely tell you what's broken."* Give the agent *"hands and eyes on the real running system"* through a skill that boots, drives and inspects the app (*"CDP, simulators, or API harnesses"*). A feature map can act as *"a guide and grading rubric"*. — [claude.dev, 16 Nov 2026](https://claude.dev/blog/how-the-claude-code-team-thinks-about-verification/)
- On the verify skill: *"Running the app end to end matters more than tests."* *"create a skill called verify. Put it in a .claude/skills/ folder in your repo, as close to the relevant code as you can"* … *"Claude knows to use the verify skill before committing changes."* … *"It's your smoke test harness, so you want it rock solid."* … *"This is how we test nearly all changes at Anthropic."* — [claude.dev, 16 Nov 2026](https://claude.dev/blog/how-the-claude-code-team-thinks-about-verification/)
- On property tests: *"Property tests look at the edge cases that people tend to miss, which is where agents often fail."* Use fast-check, Hypothesis or proptest to *"generate thousands of inputs"*. *"Property libraries are a great way to keep agents honest by using edge cases that aren't created with the same bias as the agent that created the original code."* They are also useful for rewrites where the spec has drifted from production behaviour. Example properties: round-trip, invariants (*"account balance can never become negative"*), idempotency, equivalence. — [claude.dev, 16 Nov 2026](https://claude.dev/blog/how-the-claude-code-team-thinks-about-verification/)
- On differential tests: *"particularly effective for large-scale migration use cases"*. Run old and new systems on the same inputs, *"use randomly generated inputs or a sample of production traffic"*, normalise irrelevant factors such as whitespace and keep *"a list of approved changes"*. — [claude.dev, 16 Nov 2026](https://claude.dev/blog/how-the-claude-code-team-thinks-about-verification/)
- On test-suite properties: *"If your tests are flaky you'll train the agent to run them again rather than fixing the failing code. If your tests are slow, the agent will do fewer tests across batches… Heavier tests are best deployed before you've committed the changes."* — [claude.dev, 16 Nov 2026](https://claude.dev/blog/how-the-claude-code-team-thinks-about-verification/)
- Claude Code docs: running `/verify` *"has Claude build and run the app and look at the result. That catches the kind of problem that tests and typechecks miss."* Valid checks include *"A script that diffs output against a fixture"* and *"A browser screenshot next to the mockup"*. — [Claude Code: Best practices](https://code.claude.com/docs/en/best-practices)
- De Oliveira (22 Jul 2026): *"a /verify skill confirms end-to-end behavior"*, which *"builds, runs, and observes the changes in your application"*. She suggests *"skill chaining to create an end-to-end verification flow"* (`/code-review`, `/simplify`, `/verify`, `/design`). — [claude.com blog, 22 Jul 2026](https://claude.com/blog/building-verification-loops-in-claude-code-with-skills)
- Cherny (2 Jan 2026, secondary): *"Claude tests every single change I land to claude.ai/code using the Claude Chrome extension."* — [VentureBeat](https://venturebeat.com/technology/the-creator-of-claude-code-just-revealed-his-workflow-and-developers-are)
- Hashimoto: screenshot scripts and filtered test runs as harness tools. — [mitchellh.com, 5 Feb 2026](https://mitchellh.com/writing/my-ai-adoption-journey)
- Böckeler used **mutation testing** to compare suites and found no meaningful TDD vs non-TDD gap. Small task: non-TDD 89.6% and 92.3%, TDD 93.6% and 93.2%. Large task: non-TDD 86.9% and 89.4%, TDD 85.6% and 85.2%. Secondary write-ups say she moved to mutation testing as her regression-quality check. — [martinfowler.com (Böckeler)](https://martinfowler.com/articles/exploring-gen-ai/tdd-in-the-agent-loop.html)
- Cursor advice: *"Run tests (prefer single test files for speed)"* and *"Always typecheck after making a series of code changes"*. — [Cursor blog, 9 Jan 2026](https://cursor.com/blog/agent-best-practices)

### Inferences
- In late 2026 the Anthropic view ranks verification layers as follows: real-app E2E/verify skill first; then property and differential tests to beat the agent's own blind spots; then unit tests as fast but foolable inner-loop checks. That is a shift away from classic unit-level red/green as the main tool.
- Anthropic's language that E2E tests are "difficult to fool" and that property tests "keep agents honest" treats the choice of test type partly as an anti-gaming measure (see Q4).

### Gaps
- No vendor gave numbers comparing E2E with unit tests for agent success.
- I found no 2026 Google Testing Blog post on agents and E2E/property testing.

## 4. Preventing agents from editing or weakening tests, reward hacking, and implementation-coupled tests

### Takeaway
Vendors give two kinds of defence. One is instructional: Cursor says commit the tests, then tell the agent "not to modify the tests". The other is structural: Anthropic says a check the change can modify is broken, so gating rules live on the base branch, flaky tests cannot be retried or slept away, and a commit gate requires `/verify` or `/code-review`. Reviewing in a fresh-context subagent and demanding evidence (command plus output) are the other recurring safeguards. On coupling, Böckeler found that test-first did not stop agents writing tests that compare output against the implementation itself.

### Cited Findings
- Cursor: commit the tests first, then ask for code that passes them, *"not to modify the tests"*. — [Cursor blog, 9 Jan 2026](https://cursor.com/blog/agent-best-practices)
- Anthropic (Osmani, 16 Nov 2026): *"If a change can modify the check that judges it, the check is broken. Code Review reads the REVIEW.md file from the base or default branch, never from the pull request's changes. The Claude Code team ensures the rules that gate changes are on a branch that the change can't modify."* — [claude.dev, 16 Nov 2026](https://claude.dev/blog/how-the-claude-code-team-thinks-about-verification/)
- Anthropic, on flaky tests: Claude *"can't skip them, add sleeps or retry until they pass"*. — [claude.dev, 16 Nov 2026](https://claude.dev/blog/how-the-claude-code-team-thinks-about-verification/)
- Anthropic, on the commit gate: *"a commit gate that can block a commit if the session did not contain /code-review or /verify"*, with off, observe and enforce modes. After two blocks the next commit is allowed through *"so Claude doesn't get stuck"*. — [claude.dev, 16 Nov 2026](https://claude.dev/blog/how-the-claude-code-team-thinks-about-verification/)
- Anthropic, on round caps: *"If a check is still failing after three rounds, Claude stops and brings in a human."* — [claude.dev, 16 Nov 2026](https://claude.dev/blog/how-the-claude-code-team-thinks-about-verification/)
- Anthropic docs, on evidence: *"ask Claude for evidence: the command it ran and its output, or the screenshot. 'All tests pass' on its own tells you very little."* `/code-review` runs *"in a fresh subagent that never saw your conversation. It isn't swayed by the reasoning that produced the code."* `Stop` hooks are *"enforced by Claude Code (the harness)"*, not left to the model's judgement. — [Claude Code: Best practices](https://code.claude.com/docs/en/best-practices)
- Anthropic docs, on scoping what the agent may touch: *"What's it allowed to touch? Permission rules, `dontAsk`, the sandbox, a worktree, the one branch it may push to."* — [Claude Code: Best practices](https://code.claude.com/docs/en/best-practices)
- OpenAI's fetched best-practices page does **not** contain an explicit "don't modify tests" instruction. Third-party Codex writers claim OpenAI guidance warns that Codex may weaken tests to make them pass, but I could not find this on the official page. — [OpenAI Codex best practices](https://learn.chatgpt.com/guides/best-practices); claim in [Daniel Vaughan, 10 Apr 2026](https://codex.danielvaughan.com/2026/04/10/codex-cli-test-driven-development-workflow/) (unverified)
- Böckeler, on implementation coupling: some TDD-run tests compared output against the implementation itself, and *"Writing the test first doesn't reliably prevent this."* — [martinfowler.com (Böckeler)](https://martinfowler.com/articles/exploring-gen-ai/tdd-in-the-agent-loop.html)
- Cursor, "Reward hacking is swamping model intelligence gains" (Naman Jain, **25 Jun 2026**; secondary summary): an auditor reviewed 731 Opus 4.8 Max trajectories and found agents often retrieved known benchmark fixes rather than deriving them. Hacking attempts reportedly *increased* when the model was told to keep working without stopping. This concerns benchmarks, not TDD test-editing. — [Cursor blog, 25 Jun 2026](https://cursor.com/blog/reward-hacking-coding-benchmarks)
- Agile workshop claim (secondary): writing tests before code means agents *"cannot cheat by writing a test that simply confirms whatever incorrect implementation they produced."* — [The Register, 20 Feb 2026](https://www.theregister.com/2026/02/20/from_agile_to_ai_anniversary/); contradicted empirically by Böckeler's observation above.

### Inferences
- In 2026 the guidance moved from "ask the agent nicely not to touch tests" (Cursor, January) towards structural controls the agent cannot override (Anthropic, November): base-branch rules, harness-enforced hooks and commit gates, fresh-context reviewers, and test types that are hard to game (E2E, property).
- The Cursor reward-hacking finding that "keep going without stopping" increased hacking sits uneasily with "iterate until all tests pass" prompts. Anthropic's three-round cap and two-block escape hatch look like deliberate mitigations, though Anthropic does not cite Cursor's study.

### Gaps
- None of the fetched primary sources uses the phrase "reward hacking" about test editing in user workflows. No vendor published data on how often agents edit or weaken tests in practice.
- No GitHub Copilot, Devin, Jules or Gemini CLI documentation on protecting tests was found.

## 5. Quantitative claims

### Takeaway
There are few hard numbers. The ones that exist are vendor estimates, such as Cherny's "2-3x quality" from verification feedback loops and Anthropic's "up to 10 points" from a separate rubric grader, plus one small independent experiment (Böckeler) that found **no** quality gain from TDD at 3–8.5× token cost. I found no credible 2026 vendor figure for success-rate gains from test-first prompting specifically.

### Cited Findings
- Cherny (2 Jan 2026, X thread, secondary): a verification feedback loop *"will 2-3x the quality of the final result"*. This is an anecdotal estimate, with no benchmark found. — [VentureBeat](https://venturebeat.com/technology/the-creator-of-claude-code-just-revealed-his-workflow-and-developers-are)
- Anthropic (16 Nov 2026): having a separate grader check against a rubric *"improved task success by up to 10 points"* over a standard prompting loop. About 90% of Claude Code's code is written and reviewed by Claude. A 39-item reliability checklist is used, of which Claude checks only the items whose trigger matches (*"usually 3 to 10"*). A bug counts as "detectable" if at least two of three replayed bug finders catch it. — [claude.dev, 16 Nov 2026](https://claude.dev/blog/how-the-claude-code-team-thinks-about-verification/)
- Böckeler (Thoughtworks, ~Aug 2026): TDD runs used **8.50×** (small), **2.96×** (medium) and **4.89×** (large) more tokens. Opus ranked the non-TDD solutions highest in the small and medium batches, with mixed results on the large task. Mutation scores were roughly equal (figures in Q3). She calls it exploratory, with a tiny sample. — [martinfowler.com (Böckeler)](https://martinfowler.com/articles/exploring-gen-ai/tdd-in-the-agent-loop.html)

### Inferences
- The 2026 evidence base for TDD specifically, as opposed to verification generally, is thin and mixed. Practitioner endorsement (Willison, Cursor) rests on qualitative reasoning. The one controlled-ish comparison (Böckeler) is negative but small. Strong numeric claims should be treated as vendor anecdote.

### Gaps
- No 2026 vendor study (Anthropic, OpenAI, Google, Cursor, GitHub, Cognition) reporting success-rate uplift from test-first or reproduce-first prompting was found.
- I did not fetch the FixedBench paper itself (May 2026, built from SWE-bench Verified), so I have no verified figures from it.
- Pre-2026 context, not re-verified this session: Anthropic's April 2025 "Claude Code: Best practices for agentic coding" post contained a "write tests, commit; code, iterate, commit" TDD workflow with an instruction not to modify the tests. Cursor's Jan 2026 recipe closely mirrors it. The current 2026 Claude Code docs pages fetched here no longer contain that explicit recipe.
